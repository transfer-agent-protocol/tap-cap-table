# API Reference

Base URL: `http://localhost:8293`. Requests and responses are JSON.

The product app under `/app` sends onchain writes from the issuer's wallet and uses the API for reads and metadata. Every route below can also be called directly, including the server-signed routes that write onchain with the server's key.

## Server-signed routes

Routes marked **Onchain** send a transaction from the server. They sign with `PRIVATE_KEY` from the root `.env`, and that wallet needs a role on the cap table:

- OPERATOR or ADMIN for the stakeholder, stock class, wallet, and stock transaction routes.
- ADMIN for the two authorized-share adjustments.

A cap table created with `POST /issuer/create` makes the server key its ADMIN. For a cap table minted in the app, set `NEXT_PUBLIC_OPERATOR_ADDRESS` to the server key's address before minting, or have the issuer admin grant the role later with `addOperator`. Without a role, the transaction reverts with `Does not have operator role` or `Does not have admin role`.

With `PRIVATE_KEY` unset or left as `UPDATE_ME`, the server is read-only: reads and the event poller still work, and server-signed routes fail.

<Callout type="warning">
The API doesn't authenticate callers. Anyone who can reach it can make the server sign transactions, so never expose it with a funded key.
</Callout>

## Request conventions

- Routes under `/stakeholder`, `/stock-class`, and `/transactions` look up the cap table from `issuerId` in the JSON body. That includes their GET routes, so send a body and set the method explicitly:

  ```bash
  curl -s -X GET "$API/stakeholder/id/$STAKEHOLDER_ID" \
    -H "Content-Type: application/json" \
    -d @- <<JSON
  { "issuerId": "$ISSUER_ID" }
  JSON
  ```

- Most create routes take `{ "issuerId": "...", "data": { ... } }`. `POST /issuer/create` and `POST /issuer/register` take the issuer fields at the top level.
- Bodies are validated against the pinned OCF schemas, which reject unknown fields.

## Errors

| Status | When |
| --- | --- |
| 400 | `issuerId` is missing (`issuerId is required`) or unknown (`Issuer not found`) on a route that needs it, `deployed_to` or `tx_hash` is missing on `/issuer/register`, an issuance sends more than one `share_numbers_issued` range, or the app's issuance check finds too few authorized shares or a stock class that isn't onchain. |
| 404 | The issuer doesn't exist, on `/issuer/id`, `/issuer/full`, `/cap-table/holdings/stock`, `/issuer/reconcile`, and `/issuer/poller-catchup`. |
| 500 | Everything else, including OCF validation failures and contract reverts. The body is the error message as text. |

## Scaling

The contract stores quantities, prices, and authorized-share counts as integers scaled by 1e10 (10,000,000,000).

- Send human values as strings, such as `"100000"` shares at `"4.20"`. Server-signed routes scale them before calling the contract.
- The event poller divides by 1e10 before it writes history, and `/cap-table/holdings/stock` divides the chain reads it returns.
- If you read the contract directly, divide by 1e10 yourself. A price of 4.20 is stored as `42000000000`.

## Health checks

Each router answers `GET` at its root with a short text reply: `/`, `/factory`, `/issuer`, `/cap-table`, `/stock-legend`, `/stock-plan`, `/valuation`, and `/vesting-terms`. `/stakeholder` and `/stock-class` answer too, but need an `issuerId` body like their other routes.

## Stock transactions

All of these write onchain, add history rows, and take `{ "issuerId": "...", "data": { ... } }`. Fields in parentheses are optional. Except for transfers, each returns the OCF object it validated: its `id` is a placeholder and `date` is the server's UTC date, because the contract assigns the real ids.

| Route | Role | `data` fields | Returns |
| --- | --- | --- | --- |
| `POST /transactions/issuance/stock` | OPERATOR | `stakeholder_id`, `stock_class_id`, `quantity`, `share_price`, `stock_legend_ids`, `custom_id`, `security_law_exemptions` (`comments`, `issuance_type`, `stock_plan_id`, `vesting_terms_id`, `board_approval_date`, `stockholder_approval_date`, `consideration_text`, `cost_basis`, one `share_numbers_issued` range) | `{ stockIssuance }` |
| `POST /transactions/transfer/stock` | OPERATOR | `transferorId`, `transfereeId`, `stockClassId`, `quantity`, `sharePrice`, `isBuyerVerified` | `"success"` |
| `POST /transactions/cancel/stock` | OPERATOR | `stakeholderId`, `stockClassId`, `security_id`, `quantity`, `reason_text` (`comments`) | `{ stockCancellation }` |
| `POST /transactions/retract/stock` | OPERATOR | `stakeholderId`, `stockClassId`, `security_id`, `reason_text` (`comments`) | `{ stockRetraction }` |
| `POST /transactions/reissue/stock` | OPERATOR | `stakeholderId`, `stockClassId`, `security_id`, `resulting_security_ids` (`reason_text`, `comments`) | `{ stockReissuance }` |
| `POST /transactions/repurchase/stock` | OPERATOR | `stakeholderId`, `stockClassId`, `security_id`, `quantity`, `price` (`consideration_text`, `comments`) | `{ stockRepurchase }` |
| `POST /transactions/accept/stock` | OPERATOR | `stakeholderId`, `stockClassId`, `security_id` (`comments`) | `{ stockAcceptance }` |
| `POST /transactions/adjust/issuer/authorized-shares` | ADMIN | `issuer_id`, `new_shares_authorized` (`board_approval_date`, `stockholder_approval_date`, `comments`) | `{ issuerAuthorizedSharesAdj }` |
| `POST /transactions/adjust/stock-class/authorized-shares` | ADMIN | `stock_class_id`, `new_shares_authorized` (`board_approval_date`, `stockholder_approval_date`, `comments`) | `{ stockClassAdjustment }` |

OPERATOR means OPERATOR or ADMIN. The contract assigns balance and resulting security ids, so don't send `balance_security_id` or `split_transaction_id`: validation accepts them, but they're ignored. For worked examples, see [Transfer, Cancel, and Reissue Stock](/api-guides/corporate-actions/transfer-cancel-and-reissue-stock).

`POST /transactions/issuance/stock/register-onchain` is the check the app runs before the wallet sends `issueStock`. It validates an issuance body, reads the remaining authorized shares from the contract, and saves nothing. It returns 400 when the shares don't fit or the stock class isn't onchain.

## Known issues

- Authorized-share adjustments change the contract but not the `initial_shares_authorized` saved on the issuer and stock class records in MongoDB. Read current caps from the contract, or from `GET /stock-class/id/:id`.
- Records written by older server versions can be out of date: stakeholders and stock classes from `/stakeholder/create` or `/stock-class/create` may have a MongoDB `_id` that doesn't match their onchain id, so they stay `is_onchain_synced: false` and revert in later server-signed writes (`NoStakeholder`, `InvalidStockClass`). Register each one again with `/register-onchain` under its onchain id and delete the old record. Adjustment history rows from those versions hold `new_shares_authorized` ×1e10 until a poller reindex (`POST /issuer/poller-catchup`) rewrites them.
- The contract doesn't enforce every share-cap relationship; see [Security](/security#what-the-contracts-dont-enforce).
